Selected engineering stories

// decisions, not features 05

One codebase, three platforms

1 → 3codebase to platforms

Context
An enterprise PPM platform with a mature React web app, and customers who wanted it on their phones.
Decision
Wrap the existing React codebase with Capacitor instead of starting a parallel native project.
Outcome
Android and iOS apps shipped without a separate native codebase to staff, review and keep in sync.

Three products, one system

30%faster feature delivery

Context
Three trade-tech products to build as the founding engineer, each multi-tenant and each needed in production.
Decision
Treat them as one system: a shared UI architecture and component library over modular NestJS services and multi-tenant PostgreSQL models.
Outcome
Feature delivery accelerated by 30% across products; all three reached production on infrastructure owned end to end.

The fast path to the first paint

+25%organic traffic, at Spekond

Context
Public-facing sites where page speed and discoverability are the product: a legacy PHP marketing site, and high-traffic consumer apps.
Decision
Move rendering to Next.js: SSR and static generation where each fits, route-level code splitting, deliberate work on Core Web Vitals and accessibility.
Outcome
Better page performance, Core Web Vitals and SEO at Celoxis; at Spekond the same discipline contributed to a 25% increase in organic traffic.

Rendering a Gantt at enterprise scale

4levers on the render path

Context
Gantt and analytics views carrying enterprise-scale data, where unnecessary renders directly slow the user down.
Decision
Optimise the render path itself: code splitting, lazy loading, memoization, and reusable component patterns that make the efficient approach the default.
Outcome
Data-dense views that stay responsive, and shared frontend systems that keep them that way as the product grows.
§ 06

Philosophy

// operating principles 06
Architecture is a product decision. Every boundary you draw decides what the team can ship next quarter.
  1. 01

    Speed and reliability are one budget.

    Balance delivery against reliability, security and scalability on purpose, not by accident and not after an incident.

  2. 02

    Build the system that builds the features.

    Shared components and patterns compound. Each product should cost less to build than the last.

  3. 03

    Stay close to the problem.

    The best technical decisions come from working directly with founders, product teams and the people who use the workflow.

  4. 04

    Performance is a feature users feel.

    Core Web Vitals, render paths and accessibility are not polish. They are the experience.

  5. 05

    Own it to production.

    Code is not done at merge. It is done when it is deployed, monitored and holding up under real use.
